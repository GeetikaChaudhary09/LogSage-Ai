
# ADR-0014: Logging, Monitoring and Observability Strategy

## Status

Accepted - Initial architecture decision.

## Context

LogSage AI is an application observability platform that collects, processes and analyzes telemetry from external applications.

The platform itself also consists of multiple components that require continuous operational monitoring.

These include:

- React frontend.
- Java Spring Boot backend.
- Python FastAPI ML service.
- PostgreSQL.
- Redis.
- RabbitMQ.
- Docker containers and deployment infrastructure.

Failures in these components may affect ingestion, processing, anomaly detection, incident management and user-facing operations.

The platform requires a consistent strategy for structured logging, metrics, health checks, correlation identifiers, error tracking and operational alerting.

The system must also distinguish between customer application telemetry and internal platform telemetry.

## Decision

LogSage AI will implement a centralized observability strategy covering both:

1. External application telemetry collected by LogSage AI.
2. Internal operational telemetry generated by LogSage AI itself.

The initial implementation will use structured application logs, Spring Boot Actuator, FastAPI health endpoints, infrastructure health checks and application-level metrics.

PostgreSQL will remain the source of truth for persisted customer telemetry and operational records.

Redis and RabbitMQ will support their respective caching and asynchronous processing responsibilities.

The monitoring architecture may integrate Prometheus-compatible metrics and Grafana dashboards as the platform evolves.

## Two Observability Domains

### Customer Application Observability

This domain handles telemetry submitted by external applications.

It includes:

- Application logs.
- Service information.
- Environments.
- Request and trace identifiers.
- Log volume.
- Error rates.
- Anomaly predictions.
- Incidents.
- Alert history.

Customer telemetry must remain isolated according to organization and project ownership.

### Internal Platform Observability

This domain monitors LogSage AI's own infrastructure and services.

It includes:

- Backend application health.
- Frontend availability.
- ML service health.
- PostgreSQL connectivity.
- Redis connectivity.
- RabbitMQ availability.
- Queue processing.
- API latency.
- Error rates.
- Resource utilization.
- Container health.
- Background job failures.

Internal platform telemetry must not be confused with customer application telemetry.

## Structured Application Logging

All backend services should produce structured logs.

The Java backend and Python ML service should use consistent logging fields where practical.

Initial structured log fields may include:

- timestamp
- level
- serviceName
- environment
- message
- logger
- correlationId
- requestId
- traceId
- spanId
- exceptionType
- durationMs

Logs must use UTC timestamps.

The logging format should support machine-readable JSON output in deployed environments.

Human-readable output may be used during local development.

## Log Severity

The platform will use consistent severity levels:

- TRACE
- DEBUG
- INFO
- WARN
- ERROR
- FATAL

Severity must represent the operational importance of an event.

Sensitive information must not be included merely because a higher severity level is used.

## Correlation IDs and Request Tracking

The platform must support request correlation across service boundaries.

A correlation identifier should be generated or validated at the application entry point.

The identifier should be propagated through relevant internal operations and asynchronous messages.

This will help developers trace:

- Incoming API requests.
- Backend service operations.
- RabbitMQ message processing.
- Database operations where appropriate.
- ML service requests.
- Incident and alert processing.

Untrusted client-provided correlation identifiers must be validated and handled safely.

Correlation identifiers must not be treated as authentication credentials.

## Distributed Tracing

The architecture should support distributed tracing as the platform matures.

OpenTelemetry-compatible instrumentation may be introduced for:

- HTTP requests.
- Backend service operations.
- Database interactions.
- RabbitMQ message processing.
- Backend-to-ML service calls.

Trace identifiers and span identifiers should be propagated where supported.

The initial implementation may begin with correlation IDs and request timing before full distributed tracing is introduced.

## Backend Health Monitoring

Spring Boot Actuator will provide backend health and operational endpoints.

Health indicators should cover important dependencies such as:

- PostgreSQL.
- Redis.
- RabbitMQ.
- ML service connectivity where appropriate.

Health endpoints must expose only the information required by their intended audience.

Detailed environment information and sensitive configuration must not be publicly exposed.

## ML Service Health Monitoring

The Python FastAPI service will provide health endpoints.

The monitoring strategy should distinguish:

- Process availability.
- Application readiness.
- Model artifact availability.
- Model loading status.
- Inference success.
- Inference failure.
- Prediction latency.

A running HTTP process does not necessarily mean the ML model is ready for inference.

ML service failures must not be interpreted as genuine anomaly predictions.

## Database Monitoring

PostgreSQL monitoring should cover:

- Database availability.
- Connection pool utilization.
- Query latency.
- Slow queries.
- Transaction failures.
- Database size.
- Index usage.
- Connection errors.
- Migration status.

Database monitoring must not expose customer log contents or credentials.

## Redis Monitoring

Redis monitoring should cover:

- Availability.
- Connection failures.
- Memory utilization.
- Cache hit and miss behaviour.
- Evictions.
- Command latency.
- Rate-limiting operations.

Redis failures must be handled according to the specific operation's reliability requirements.

Persistent application records must never depend exclusively on Redis.

## RabbitMQ Monitoring

RabbitMQ monitoring should cover:

- Broker availability.
- Queue depth.
- Message publishing rate.
- Message consumption rate.
- Unacknowledged messages.
- Retry counts.
- Dead Letter Queue depth.
- Consumer availability.
- Message processing latency.

Queue growth and repeated processing failures should generate operational signals.

Messages must not be acknowledged before required persistence operations succeed.

## Application Metrics

The backend should expose application-level operational metrics.

Examples include:

- HTTP request count.
- HTTP error count.
- Request latency.
- Active requests.
- Authentication failures.
- API key validation failures.
- Ingestion requests.
- Accepted log events.
- Rejected log events.
- Database operation latency.
- RabbitMQ publishing failures.
- Consumer processing failures.
- Anomaly inference requests.
- ML inference failures.
- Incident creation count.
- Alert evaluation count.

Metrics must use bounded labels.

High-cardinality values such as raw messages, user identifiers, API keys and arbitrary request IDs must not be used as metric labels.

## Ingestion Pipeline Monitoring

The ingestion pipeline must expose measurements for:

- Incoming requests.
- Authenticated requests.
- Rejected requests.
- Accepted log events.
- Queue publishing failures.
- Queue depth.
- Processing latency.
- Persistence failures.
- Duplicate events.
- Retry counts.
- Dead Letter Queue messages.

The system must distinguish accepted requests from successfully persisted logs.

A successful HTTP acceptance response must not be interpreted as proof that all downstream processing has completed.

## ML Monitoring

The ML service should expose:

- Model version.
- Model loading status.
- Inference request count.
- Successful inference count.
- Failed inference count.
- Inference latency.
- Feature validation failures.
- Prediction distribution.
- Model artifact availability.

Model performance evaluation should use appropriately labelled validation data.

Synthetic training and testing datasets must be identified as synthetic.

Prediction counts alone must not be presented as proof of model accuracy.

## Frontend Monitoring

Frontend operational monitoring should cover:

- Application availability.
- JavaScript runtime errors.
- Failed API requests.
- API response latency.
- Build and deployment status.
- Critical user workflow failures.

Sensitive user information, credentials and raw customer log messages must not be unnecessarily captured in frontend monitoring events.

## Metrics Collection and Visualization

The architecture should support a Prometheus-compatible metrics collection model.

Grafana may be used for internal infrastructure and operational dashboards.

Potential dashboard categories include:

### Platform Overview

- Service availability.
- API request rate.
- Error rate.
- Request latency.
- Resource utilization.

### Ingestion Health

- Ingestion request rate.
- Accepted and rejected events.
- Queue depth.
- Processing latency.
- Persistence failures.

### Infrastructure Health

- PostgreSQL status.
- Redis status.
- RabbitMQ status.
- Container health.
- CPU and memory utilization.

### ML Operations

- Model availability.
- Inference latency.
- Prediction counts.
- Inference failures.

These dashboards must use actual collected metrics.

Unavailable measurements must not be represented as fabricated zero values.

## Error Tracking and Exception Handling

The platform must capture actionable operational errors.

Error records should include:

- Timestamp.
- Service.
- Error category.
- Exception type.
- Correlation identifier.
- Relevant operational context.

Stack traces may be recorded in restricted application logs where appropriate.

Sensitive request bodies, credentials and personal information must be redacted.

Repeated failures should be grouped or summarized where possible to avoid excessive alert noise.

## Internal Operational Alerts

Internal monitoring should support alerts for important platform conditions.

Examples include:

- Backend service unavailable.
- ML service unavailable.
- PostgreSQL connectivity failure.
- RabbitMQ unavailable.
- Queue backlog exceeding configured limits.
- Repeated message processing failures.
- High API error rate.
- Excessive request latency.
- Container restart loops.
- Persistent resource exhaustion.

Internal platform alerts must be distinguishable from customer-configured alert rules.

## Security and Data Protection

- Redact API keys.
- Never log passwords or raw refresh tokens.
- Avoid logging JWT credentials.
- Protect internal health endpoints.
- Restrict access to operational dashboards.
- Avoid sensitive data in metric labels.
- Apply appropriate log retention.
- Restrict access to internal platform telemetry.
- Prevent customer organization data from leaking into unrelated monitoring contexts.

## Retention and Storage

Customer log retention and internal platform log retention must have separately defined policies.

The platform should support configurable retention according to storage capacity and operational requirements.

Retention jobs must not delete records outside their authorized scope.

Backup and recovery policies must remain consistent with the data retention strategy.

## Failure Handling

The monitoring system must not become a critical dependency for log ingestion.

If a monitoring or metrics backend becomes unavailable:

- Core ingestion should continue where possible.
- Customer telemetry must not be discarded merely because a dashboard is unavailable.
- Operational failures should be reported through available fallback mechanisms.
- Monitoring recovery should not create uncontrolled processing backlogs.

Internal monitoring failures must be distinguishable from application failures.

## Testing Requirements

Planned observability tests:

- Structured logging output.
- UTC timestamp handling.
- Sensitive field redaction.
- Correlation ID generation.
- Correlation ID propagation.
- Backend health endpoints.
- ML health and readiness endpoints.
- PostgreSQL health monitoring.
- Redis health monitoring.
- RabbitMQ health monitoring.
- Queue depth metrics.
- Ingestion metrics.
- Request latency metrics.
- Exception logging.
- Internal alert evaluation.
- Monitoring failure without ingestion interruption.
- Organization and project telemetry isolation.

## Alternatives Considered

### Unstructured Console Logging

Rejected as the only logging strategy because it makes automated filtering and operational analysis more difficult.

### Monitoring Only Customer Applications

Rejected because the observability platform itself must also remain operational and reliable.

### Full Distributed Tracing from Day One

Not selected as a mandatory initial requirement because it introduces additional instrumentation and infrastructure complexity.

Correlation IDs and structured logs will provide the initial foundation.

### Prometheus-Compatible Metrics

Selected as the intended metrics integration model because it supports standardized collection and dashboarding.

## Consequences

### Positive

- Better internal platform visibility.
- Easier failure diagnosis.
- Consistent structured logging.
- Cross-service request correlation.
- Better infrastructure monitoring.
- Improved operational alerting.
- Clear separation of customer and internal telemetry.
- Better incident investigation.

### Negative

- Additional monitoring configuration.
- Storage and processing overhead.
- Metrics cardinality requires careful control.
- Sensitive data redaction requires consistent enforcement.
- Monitoring infrastructure introduces operational complexity.

## Implementation Notes

- Use structured JSON logging in deployed environments.
- Use Spring Boot Actuator for backend health.
- Add FastAPI health and readiness endpoints.
- Introduce correlation ID propagation.
- Monitor PostgreSQL, Redis and RabbitMQ.
- Add application-level metrics.
- Evaluate OpenTelemetry instrumentation.
- Evaluate Prometheus and Grafana integration.
- Keep internal and customer telemetry logically separated.
- Add operational alerting for critical failures.
- Verify that monitoring failures do not block core ingestion.

## Review Conditions

Revisit this decision if:

- Observability infrastructure changes.
- Monitoring volume increases significantly.
- Distributed tracing becomes mandatory.
- Retention requirements change.
- Security requirements change.
- Operational testing identifies monitoring gaps.
